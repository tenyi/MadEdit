# ADR 0012：超長單行的語法突顯演算法（可見視窗 + Oniguruma）

- 狀態：已採納
- 日期：2026-10-27
- 關聯：[ADR 0005](0005-syntax-highlighting-engine.md)、[ADR 0011](0011-egui-rewrite.md)

## 背景

`example.js`（1.99 MB、180 行、最長一行 158,953 位元組；以
`scripts/make_example_js.py` 產生的合成樣本）在編輯時仍會卡頓。
前一輪（`ae32b15`）已把超長行截斷成「只解析前 16 KB」，仍無法接受：

| 操作（NoWrap，離屏 harness） | 耗時 |
| --- | --- |
| 按鍵 | 65 ms |
| 移到行尾（End） | 61 ms |
| 5 次 PageDown | 593 ms（每幀約 119 ms） |
| 點選放置游標 | 166 ms |
| 開檔＋首繪 | 517 ms |

把耗時拆開量測後， `SyntaxCache::highlight` 佔其中的 90% 以上：單一可見行就 10–165 ms，
繪製只有 0.03–13 ms。因此問題不在 UI，而在突顯演算法本身。

### 為什麼 syntect 一定會慢

`syntect` 是 TextMate 文法引擎：逐行把整行文字交給一組 Oniguruma/`fancy-regex`
規則比對，狀態（rule stack）只在**行**之間傳遞。實測（同一行、JavaScript 文法）：

| 解析長度 | `regex-fancy` | `regex-onig` |
| --- | --- | --- |
| 256 B | 0.52 ms | 0.14 ms |
| 1 KB | 3.24 ms | 0.86 ms |
| 4 KB | 13.99 ms | 3.75 ms |
| 16 KB | 55.9 ms | 13.4 ms |
| 159 KB（整行） | 507 ms | 108 ms |

三個結構性事實：

1. 成本 ≈ 3 µs/位元組（`fancy-regex`），與行長成正比。
2. `ParseState::parse_line` **無法從行內中斷處接續**；任何「快取行內檢查點」的作法都
   必須先把該行從頭掃到檢查點，對超長行沒有意義。
3. 只有**行**粒度有語法狀態；行內的可見範圍無法單獨求解。

### 其他編輯器怎麼做

| 引擎 | 作法 | 對本專案的適用性 |
| --- | --- | --- |
| VSCode / TextMate | 逐行規則比對（Oniguruma），並以 `editor.maxTokenizationLineLength`（預設 20,000 字元）**放棄**更長的行 | 概念可借用，但整行放棄會讓畫面完全沒顏色 |
| tree-sitter（Helix、Neovim） | 增量 GLR 剖析，只重剖析變動位元組到下一個 token 邊界，查詢只跑變動與可見範圍 | 演算法上最正確，但要為 30+ 語言內嵌文法與查詢、重寫對色與主題對應，不是本專案 KISS 原則下的一步 |
| 自寫 lexer / Pygments 類 | 全檔 token 化 | 不支援多語法廣度，且仍是 O(行長) |

結論：**任何精確演算法都必須掃描整行**。要讓每次按鍵的成本與行長無關，只能讓
「送進引擎的位元組數」與可見字元數成正比，也就是只剖析可見視窗。

## 決策

1. **改用 Oniguruma 後端**：`syntect` feature 由 `regex-fancy` 改為 `regex-onig`
   （`onig` crate，內嵌 Oniguruma，BSD 授權）。TextMate 文法本來就是為
   Oniguruma 設計的，同一份文法快 4.2 倍（3 µs → 0.72 µs/位元組）。
   這是全域的改進（一般檔案按鍵、開檔、捲動都受益），不只是超長行。
2. **超長行只剖析「可見視窗」**（`src/core/syntax.rs`）：
   - 行長 > `WINDOW_LINE_BYTES`（2 KB）且為互動呼叫時，只剖析畫面可見字元範圍
     前後各留白的一段：起點對齊 `WINDOW_ALIGN`（256 B）格，並往前 64 B 內找最近的
     語句邊界（`;` `{` `}`）當起點，讓語法上下文盡量回到基底狀態；視窗本體
     `WINDOW_BYTES`（1 KB）。
   - 視窗兩端都必須對齊 UTF-8 字元邊界：256 位元組格線與「往回的 `;` `{` `}`」都可能落在
     全形字中間（`本` 的位元組範圍是 2303..2306），直接切片會 panic。
     起點往前對齊後仍不得超過可見範圍起點，終點取「格線終點」與「可見終點」的較大值。
   - 視窗之前的字元由 `HighlightSpan::skip_chars` 表示（不複製文字），繪製時以前景色。
   - 視窗結果以**行內容雜湊**驗證：編輯別的行不會重建它；水平捲動在同一格內不重建。
   - 超長行對「跨行解析狀態」透明（不消耗也不產生狀態），因此在超長行內編輯
     不會連帶重解析它後面的行，狀態仍確定可收斂。
   - 列印（`highlight_full`）沒有視窗資訊，仍取整行；超過 16 KB 時只解析前 16 KB。
3. **行版面跨幀快取**（`src/app/view/layout.rs`）：`chars` + 每字元 x 座標對 158 KB 的行
   要 3–8 ms，原本每幀重建。改為依內容雜湊跨幀沿用（`ViewState::begin_frame`
   設定版本、丟掉上一幀沒用到的行），只有被改到的行重建。

## 後果

`cargo test --release benchmark_long_line_ -- --ignored --nocapture`（離屏軟體繪製，
不含原生視窗與 GPU 呈現；樣本檔以 `python3 scripts/make_example_js.py` 產生：
1,993,854 位元組、180 行、最長一行 158,953 位元組，行內含數萬字元的中文字串）：

| 操作 | 之前 | 之後 |
| --- | --- | --- |
| 按鍵（NoWrap / ByWindow） | 65.3 / 62.1 ms | 6.1 / 1.5 ms |
| 移到行尾 | 61.3 / 93.5 ms | 22.2 / 20.3 ms |
| Shift+End 選取 | 224.9 / 184.2 ms | 41.5 / 36.7 ms |
| 5 次 PageDown | 593.4 / 578.8 ms | 6.3 / 1.6 ms |
| 點選 | 166.5 / 193.4 ms | 0.6 / 0.6 ms |
| 開檔＋首繪 | 517.1 / 121.2 ms | 130.7 / 64.8 ms |

- 「移到行尾」的 20–40 ms 有 11 ms 落在 `view::show` 之外（egui 分塊／字形快取），
  且**只有第一次大幅跳躍**如此；同一位置再按 End 為 3 ms。
- 第一次剖析某語言會付一次正規表示式編譯成本（> 8 ms），該幀以分時預算延後補色。

### 已知限制

- 視窗外的行內文字不著色（以前景色顯示）；與 VSCode 的整行放棄相比，
  至少「正在看的那一段」一定有顏色。
- 若可見區域起點落在跨行字串／區塊註解內，視窗起點的上下文是猜的
  （以語句邊界回退降低誤差）。整行 ≤ 2 KB 時仍是精確解析。
- 超長行若含有跨行結構，後面幾行可能著色不正確（例如行內有未關閉的範本字串）。
  這是「行狀態透明」換來的穩定性。
- 水平捲動每跨過 256 B 的格、頁面換一整批超長行時會重建視窗；
  一頁全部是超長行時仍由每幀 8 ms 預算分幾幀補完。

### 後續可做

- 換行模式下一整頁同一超長行時，依「離游標遠近」逐列補色（目前一次補完整頁）。
- 把行版面限制在可見字元範圍，讓 30 行 × 158 KB 的極端頁面也維持 O(可見)。
